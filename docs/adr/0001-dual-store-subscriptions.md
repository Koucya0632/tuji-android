# ADR-0001：同一個帳號在兩個商店都訂閱時，擋在購買前

- 狀態：已接受
- 日期：2026-09-09
- 決定者：使用者（2026-09-09 拍板）

## 背景

Tuji 的帳號是 Supabase 的帳號，**不是** App Store 或 Play 的帳號。同一個人可以
在 iPhone 上用 Apple ID 訂閱、再在 Android 上用同一個 Tuji 帳號登入。兩邊的
訂閱是兩個商店各自收錢，Tuji 這邊看到的是同一個 `user_id`。

現在的資料表擋不住這件事：

```sql
CREATE TABLE user_entitlements (
  user_id                 UUID PRIMARY KEY,   -- 一個使用者一列
  tier                    TEXT,
  source                  TEXT,               -- 'appstore'
  expires_at              TIMESTAMPTZ,
  original_transaction_id TEXT,               -- 一個交易 id
  ...
)
```

`user_id` 是主鍵、`original_transaction_id` 上有 UNIQUE 索引。**兩份有效訂閱
表達不了**：第二筆寫進來會覆蓋第一筆，或撞上唯一索引。

而 Tuji 沒有任何一邊能主動退款給另一邊 —— Apple 的錢只有 Apple 能退，Google
的只有 Google 能退。所以一旦兩邊同時扣款，處理成本是人工的，而且是每一筆。

## 決定

**付費牆在發起購買之前先問伺服器，已經有另一個商店的有效訂閱就不讓買。**

```
使用者按下訂閱
  → 讀 /api/atlas/entitlement
  → plan == "pro" 且 source 不是這個平台
      → 不啟動 Billing 流程
      → 告訴他權益已經生效，以及去哪裡管理（App Store 訂閱頁）
  → 否則才進 Play Billing
```

## 為什麼不是另外兩個選項

**「允許並取較晚到期者」** 需要把 `user_entitlements` 改成一個使用者多列、
每個 store 一列，權益取聯集。功能上最完整，但它接受了「兩邊同時扣款」這件事
會發生，於是每一次都要有人去看是誰該退。**Tuji 是一個人維護的 App**，那個人工
成本沒有上限。

**「允許但只認先到的」** 最糟：第二筆訂閱照樣扣款、卻不給任何額外權益。那不是
技術債，那是收了錢不給東西，會直接變成客訴與退款。

擋在購買前的代價是**少數真的想換商店的人會被擋一次**，而他要做的是先在原本的
商店取消。那是一個一次性的、可以用一句話說清楚的不便，而不是一筆爛帳。

## 後果

- **後端要多回一個欄位。** `/api/atlas/entitlement` 目前只回 `plan` 與到期日，
  沒有 `source`。付費牆需要它才知道「Pro 是從哪來的」，否則只能顯示一句
  「你已經是 Pro」而說不出去哪裡管理。這是 M4 後端工作的一部分。
- **`source` 的值要能對應到平台。** 現在只有 `'appstore'`；Google 那條會寫
  `'play'`。判斷「是不是這個平台」的規則是純函式，見 `PurchaseGate`。
- **手動補發（grant）不算另一個商店。** 被補發 Pro 的人如果想真的訂閱，不該
  被擋 —— 那不是雙重扣款。所以規則比對的是 store 來源，不是 `plan == pro`。
- **這個決定不需要改 schema。** 一個使用者一列站得住，因為第二份訂閱不會存在。
- 如果哪天真的要支援換商店，那時再改成多列；到那時已經有真實的使用者行為資料
  可以判斷值不值得。
